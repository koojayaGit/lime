# ZERO TO ONE --- 구현 요구사항

> 문서 목적: 앱 개발 및 테스트 과정에서 기능·품질·기술 요구사항을
> 일관되게 관리한다.\
> 상태: 초기 요구사항 초안(v1.0). 세부 조건과 우선순위는 개발 과정에서
> 확정한다.

## 1. 제품 범위와 기본 전제

-   초기 사용자는 개인 사용자 1명이다.
-   향후 지인 등 복수 사용자가 각자 계정을 만들어 사용할 수 있어야 한다.
-   PC와 스마트폰에서 모두 사용할 수 있어야 한다.
-   기업 발굴과 분석, 성장 추적이 핵심이며 포트폴리오 관리는 보조
    기능이다.
-   라이트 모드와 다크 모드를 지원한다.

## 2. 기능 요구사항 (FR)

### FR-01. 계정 및 사용자 관리

-   [ ] 사용자는 계정을 생성하고 로그인할 수 있어야 한다.
-   [ ] 사용자는 로그아웃할 수 있어야 한다.
-   [ ] 사용자별 개인 데이터가 분리되어야 한다.
-   [ ] 향후 사용자 초대 및 다중 사용자 이용이 가능하도록 설계해야 한다.
-   [ ] 다른 사용자의 비공개 포트폴리오·투자 가설·연구 기록에 접근할 수
    없어야 한다.

### FR-02. 기업 관리

-   [ ] 사용자는 보유 여부와 관계없이 기업을 등록할 수 있어야 한다.
-   [ ] 기업명, 국가, 시장, 티커, 산업 등 기본정보를 관리할 수 있어야
    한다.
-   [ ] 기업을 조회·수정·삭제할 수 있어야 한다.
-   [ ] 기업과 상장 증권을 구분해 관리해야 한다.
-   [ ] 기업별 상세 페이지를 제공해야 한다.

### FR-03. Discovery 및 관심종목

-   [x] 새롭게 발굴한 기업을 Research와 분리된 관심종목으로 등록하고 삭제할 수 있어야 한다.
-   [x] 관심종목의 발굴 이유와 등록일을 기록해야 한다.
-   [x] 검토 상태와 씨앗주·새싹주·성장주·기둥주·열매주 단계를 관리해야 한다.
-   [x] 관심종목을 검색하고 성장 단계로 필터링할 수 있어야 한다.
-   [x] 현재가를 표시하고 매수 목표가, 시가총액, PER, 배당률, 연간 주당 배당금, EPS를 기록할 수 있어야 한다.
-   [ ] 재무 지표는 출처와 기준일을 함께 표시해야 한다.
-   [ ] 관심종목별 알림 조건을 설정할 수 있어야 한다.

### FR-04. 기업 Research

-   [ ] 기업별로 다음 5개 영역을 평가할 수 있어야 한다.
    -   Market & Industry
    -   Technology & Moat
    -   CEO & Management
    -   Growth & R&D
    -   Financial Structure
-   [ ] 각 평가 영역에 점수와 평가 근거를 기록할 수 있어야 한다.
-   [ ] Innovation Score와 Execution Score를 구분해 관리할 수 있어야
    한다.
-   [ ] 과거 평가와 현재 평가를 비교할 수 있어야 한다.
-   [ ] 점수만으로 매수·매도 판단을 자동화하지 않아야 한다.

### FR-05. 기업 성장 단계

-   [ ] 기업을 씨앗주·새싹주·성장주·기둥주·열매주로 분류할 수 있어야
    한다.
-   [ ] 성장 단계 변경 날짜와 변경 이유를 기록해야 한다.
-   [ ] 단계 변경의 근거가 되는 실적·기술·고객·계약 등의 자료를 연결할
    수 있어야 한다.
-   [ ] 성장 단계는 주가 등락만으로 자동 변경하지 않아야 한다.
-   [ ] 과거 단계 변경 이력을 확인할 수 있어야 한다.

### FR-06. Investment Thesis

-   [ ] 기업별 최초 투자 가설을 기록할 수 있어야 한다.
-   [ ] 투자 이유와 기대하는 변화 또는 성장 경로를 기록할 수 있어야
    한다.
-   [ ] 성공 조건을 기록할 수 있어야 한다.
-   [ ] 위험 요인과 가설 무효화 조건을 기록할 수 있어야 한다.
-   [ ] 가설 수정 및 검증 이력을 보존해야 한다.
-   [ ] 최초 가설과 현재 판단을 비교할 수 있어야 한다.

### FR-07. Timeline 및 Monitoring

-   [ ] 기업별 주요 사건을 시간순으로 기록할 수 있어야 한다.
-   [ ] 실적 발표, 공시, 기술 개발, 제품 출시, 계약, 고객 확보, 인허가,
    경쟁사 변화 등을 기록할 수 있어야 한다.
-   [ ] 이벤트의 발생일과 기록일을 구분할 수 있어야 한다.
-   [ ] 이벤트에 출처와 관련 자료를 첨부할 수 있어야 한다.
-   [ ] 사용자가 직접 기록한 내용과 외부에서 수집한 내용을 구분해야
    한다.

### FR-08. 알림

-   [ ] 관심종목별 알림을 설정할 수 있어야 한다.
-   [ ] 목표 가격 도달 알림을 지원해야 한다.
-   [ ] 사용자가 지정한 등락률 조건 알림을 지원해야 한다.
-   [ ] 실적 발표 및 공시 알림을 지원하도록 설계해야 한다.
-   [ ] 기업 관련 뉴스와 주요 성장 이벤트 알림을 지원하도록 설계해야
    한다.
-   [ ] 사용자가 직접 정의한 알림 조건을 추후 확장할 수 있어야 한다.
-   [ ] 앱 내부 알림센터를 제공해야 한다.
-   [ ] PC 브라우저 알림과 모바일 푸시 알림을 지원 가능한 환경에서
    제공해야 한다.
-   [ ] 알림 종류별 수신 여부를 사용자가 설정할 수 있어야 한다.
-   [ ] 알림에 발생 시점과 가능한 경우 데이터 출처를 표시해야 한다.
-   [ ] 동일 이벤트가 반복 수신되는 문제를 줄이기 위한 중복 방지 정책이
    필요하다.

### FR-09. Portfolio

-   [x] 한국 및 미국 주식을 등록할 수 있어야 한다.
-   [x] 종목별 보유 수량과 평균 매입가를 관리할 수 있어야 한다.
-   [ ] 매수·매도 거래 내역을 기록할 수 있어야 한다.
-   [x] 현재가 API를 바탕으로 평가금액, 손익, 수익률을 계산해야 한다.
-   [x] 필요한 경우 환율을 반영한 통화별 및 통합 현황을 제공해야 한다.
-   [x] 현금 잔액을 별도 관리하고 총자산 및 자산 비중에 포함해야 한다.
-   [x] 보유 종목의 5단계 성장 분류를 관리하고 단계별 주식 비중을 보여줘야 한다.
-   [x] 일부 시세 또는 환율이 없을 때 총자산 및 전체 비중 계산을 보류해야 한다.
-   [ ] 배당금 기록을 관리할 수 있어야 한다.
-   [x] 보유 증권에서 같은 티커의 기업 Research로 이동할 수 있어야 한다.

### FR-10. Dashboard

-   [ ] 성장 단계별 기업 수와 분포를 보여줘야 한다.
-   [ ] 최근 연구 업데이트와 주요 이벤트를 보여줘야 한다.
-   [ ] 투자 가설 변경 및 검증이 필요한 기업을 확인할 수 있어야 한다.
-   [ ] 관심종목 알림과 주요 모니터링 항목을 확인할 수 있어야 한다.
-   [ ] 포트폴리오 요약은 제공하되 기업 성장 현황을 우선 배치해야 한다.

### FR-11. 데이터 내보내기 및 복원

-   [ ] 사용자가 자신의 주요 데이터를 내보낼 수 있는 방안을 마련해야
    한다.
-   [ ] 데이터 백업 및 복원 절차를 마련해야 한다.
-   [ ] 삭제나 수정 작업에서 실수로 데이터가 손실되지 않도록 확인 절차를
    고려해야 한다.

### FR-12. 향후 공유 기능

-   [ ] 향후 사용자가 특정 기업 분석 보고서를 선택적으로 공유할 수
    있도록 데이터 구조를 고려한다.
-   [ ] 공유 기능을 도입할 경우 공유 범위와 권한을 사용자가 명확히
    제어할 수 있어야 한다.
-   [ ] 기본값은 개인 기록 비공개로 한다.

## 3. 비기능 요구사항 (NFR)

### NFR-01. 호환성 및 반응형

-   [ ] 데스크톱 브라우저에서 정상 동작해야 한다.
-   [ ] 스마트폰 브라우저에서 정상 동작해야 한다.
-   [ ] 화면 크기에 따라 레이아웃이 적절히 변경되어야 한다.
-   [ ] 지원 가능한 환경에서 PWA 설치 경험을 제공해야 한다.

### NFR-02. 사용성

-   [ ] 기업 등록과 핵심 정보 확인이 직관적이어야 한다.
-   [ ] PC에서는 비교·분석에 적합한 정보 밀도를 제공해야 한다.
-   [ ] 모바일에서는 조회와 간단한 기록에 적합한 화면을 제공해야 한다.
-   [ ] 라이트·다크 모드 모두 가독성을 확보해야 한다.
-   [ ] 검색, 정렬, 필터 기능을 일관되게 제공해야 한다.

### NFR-03. 성능 및 안정성

-   [ ] 일반적인 화면 전환과 데이터 조회가 원활해야 한다.
-   [ ] 데이터 저장 중 오류가 발생하면 사용자에게 상태를 알려야 한다.
-   [ ] 저장 실패를 성공으로 표시하지 않아야 한다.
-   [ ] 새로고침이나 재접속 후 저장된 데이터가 유지되어야 한다.
-   [ ] 핵심 데이터 변경 작업은 오류 및 중복 처리에 안전해야 한다.

### NFR-04. 보안 및 개인정보

-   [ ] 인증되지 않은 사용자는 개인 데이터에 접근할 수 없어야 한다.
-   [ ] 사용자별 데이터 접근 권한을 서버 측에서 검증해야 한다.
-   [ ] RLS 등 데이터베이스 접근 제어를 적용해야 한다.
-   [ ] 비밀키·비밀번호·토큰을 소스 코드에 직접 작성하지 않아야 한다.
-   [ ] 개인 데이터는 기본적으로 다른 사용자에게 공개되지 않아야 한다.

### NFR-05. 데이터 신뢰성

-   [ ] 외부 데이터의 출처와 기준 시점을 가능한 범위에서 표시해야 한다.
-   [ ] 데이터 수집 실패 또는 갱신 지연을 명확히 표시해야 한다.
-   [ ] 실시간 데이터가 아닌 값을 실시간인 것처럼 표시하지 않아야 한다.
-   [ ] 자동 수집 정보와 사용자 입력 정보를 구분해야 한다.
-   [ ] AI 분석은 참고 자료로 취급하고 근거 및 분석 시점을 남길 수
    있어야 한다.

### NFR-06. 확장성 및 유지보수성

-   [ ] 개인용으로 시작하되 다중 사용자 구조로 확장할 수 있어야 한다.
-   [ ] 기업과 증권, 공통 데이터와 개인 데이터를 분리해야 한다.
-   [ ] 기능별 코드 구조를 유지해 개별 기능을 독립적으로 개선할 수
    있어야 한다.
-   [ ] 외부 API 공급자를 교체하거나 추가하기 쉬운 구조를 지향한다.

## 4. 기술 및 운영 요구사항 (TR)

### TR-01. 개발 환경

-   [ ] VS Code를 기본 개발 환경으로 사용한다.
-   [ ] Codex를 개발 보조 도구로 활용한다.
-   [ ] Git으로 모든 소스 코드 변경 이력을 관리한다.
-   [ ] GitHub Private Repository를 사용한다.

### TR-02. 브랜치 및 버전 관리

-   [ ] `main`은 안정 버전을 유지한다.
-   [ ] `develop`은 개발 통합 브랜치로 사용한다.
-   [ ] 개별 기능은 `feature/*` 브랜치에서 개발한다.
-   [ ] 검증된 변경사항만 통합한다.
-   [ ] 안정 버전은 태그 등으로 보존한다.
-   [ ] `.gitignore`를 설정한다.
-   [ ] 환경변수와 비밀정보를 저장소에 커밋하지 않는다.

### TR-03. 권장 기술 스택

-   [ ] 프론트엔드: React + TypeScript + Vite
-   [ ] 데이터베이스: Supabase PostgreSQL
-   [ ] 인증: Supabase Auth
-   [ ] 접근 제어: PostgreSQL RLS
-   [ ] 설치 경험: PWA
-   [ ] 배포 및 외부 API 공급자는 별도 검토 후 확정한다.

### TR-04. 테스트

-   [ ] 기업 생성·조회·수정·삭제 테스트
-   [ ] 관심종목 등록 및 알림 설정 테스트
-   [ ] 평가 점수와 성장 단계 이력 테스트
-   [ ] 투자 가설 및 타임라인 저장 테스트
-   [ ] 포트폴리오 계산 검증
-   [ ] PC·모바일 반응형 테스트
-   [ ] 라이트·다크 모드 테스트
-   [ ] 서로 다른 사용자 계정 간 데이터 격리 테스트
-   [ ] API 오류·네트워크 중단·저장 실패 테스트
-   [ ] 기존 기능에 대한 회귀 테스트

## 7. 완료 기준

각 기능은 화면에 표시되는 것만으로 완료 처리하지 않는다. 다음 조건을
확인해야 한다.

1.  사용자가 실제로 기능을 실행할 수 있다.
2.  데이터가 의도한 위치에 정확히 저장된다.
3.  새로고침과 재접속 후에도 데이터가 유지된다.
4.  수정과 삭제가 정상 동작한다.
5.  오류가 발생하면 정확한 상태와 안내가 제공된다.
6.  PC와 모바일에서 핵심 사용 흐름이 동작한다.
7.  사용자별 권한이 올바르게 적용된다.
8.  기존 기능이 손상되지 않았음을 테스트한다.
